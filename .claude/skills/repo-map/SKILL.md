## API routes

Mounted under `src/app/api/**`. Notable groups:

- `api/auth/[...nextauth]` — NextAuth handler
- `api/session-state` (GET - returns `{ version }`, the per-sign-in `sessionVersion` stamped into the JWT. `SessionFreshness` (`src/components/session-freshness.tsx`) polls it on focus, visibility change and a `click:session-changed` storage ping, then reloads when the version moved - so a second tab never keeps rendering the previous account after an account switch or a sign-out. Read-only by contract: it must not refresh a stale session cookie, which is also why `src/proxy.ts` strips Auth.js session refreshes off every proxy response via `withoutSessionRefreshCookies`)
- `api/notifications/unread-count` (GET - returns `{ count, countedAt }` for the signed-in user, 401 without a session, `private, no-store`. `HeaderNotificationsBell` fetches it on every client-side navigation and on focus / visibility change, because the bell renders in the root layout and a layout does not re-render on navigation - before this, a mutual click formed after the last full page load never reached the badge. `countedAt` is the database clock, so the bell keeps whichever count was taken last: a layout re-render from a revalidating action beats an older fetch)
- `api/clicks/coordination` (GET - returns `{ entry, catalogue }`, what the coordination drawer needs to open over any page: `entry` is a `ProposalEntry` or `null`, `catalogue` the picker's curated events. `?with=<profileId>` = the viewer's UNSEEN active mutual with that person (`getUnseenMutualReveal` - not blocked, not muted); `?id=<mutualId>` = that mutual re-read (`getCoordinationEntry`). 400 on a missing/non-UUID param, 401 without a session, `private, no-store`. Its one caller is `MutualRevealHost` (`src/components/mutual-reveal-host.tsx`, root layout, inside `ChromeGate`): when a click form fires `click:sent` naming the person it clicked, it asks `?with=` and, for a mutual that send COMPLETED, opens `CoordinationDrawer` in place over the current page - reveal first, then every step after it without a route change - and asks `?id=` after each drawer action, since those revalidate only `/proposals`. It never reads on navigation: the side that was WAITING meets its reveal by opening it (notification, dashboard banner, Your clicks, email - all `/proposals?open=<mutualId>`). Replaced `api/clicks/reveal` (2026-09-29). §6.1-safe: the send's reply is untouched and identical for every outcome; this is a separate read after commit)
- `api/clicks/picks` (GET `?mutual=<mutualId>` - returns `{ events }`, Click's matched picks for ONE pair, the pool behind S5's "Show another" in the coordination drawer (`SuggestPlan` in `src/components/coordination-drawer.tsx`). `getMatchedPicksForMutual`: the viewer must be one of the pair (otherwise an empty list, never "not yours"), same ranking as the pick a mutual opens on (`pairPicksSql`, shared with `sendClickInner`), never a night either of them already holds a seat on, capped at 6 (`MATCHED_PICKS_LIMIT`). Rows are `ProposalCatalogueEvent` card facts - no score, no rank. 400 on a missing/non-UUID param, 401 without a session, `private, no-store`)
- `api/admin/events`, `api/admin/events/[eventId]/approve` (approving also flips the owning merchant's `auto_approve_events` flag on - their future events then publish straight to `live`, skipping the pending queue; see below), `api/admin/events/[eventId]/reject` (declines a pending event → `rejected`; optional `{ reason }` body rides through to the merchant email + audit log), `api/admin/merchants/[merchantId]/verification`, `api/admin/merchants/[merchantId]/auto-approve` (`{ autoApprove: boolean }` - admins grant/revoke a merchant's trusted status), `api/admin/tags` (POST upsert, PATCH edit by `{ id }` keeping the slug stable, DELETE `?id=` removes the tag + its `event_tags`/`user_tags` links), `api/admin/tag-requests/[requestId]` (POST `{ action: "approve", label, categoryName }` | `{ action: "dismiss", note? }` - works one host tag request off the `/admin/tags` queue via `decideTagRequestForAdmin`. Approve links an existing tag with that slug, else creates an interest tag through `createTagForAdmin`; either way the host gets an in-app notification. Needs `database/068_tag_requests.sql`; answers 503 until it is applied)
- `api/admin/members/out-of-area` (GET - the out-of-area waitlist as a CSV download: name, email, postcode, suburb, state, joined date for every member whose saved suburb is outside the attendee pilot, via `getOutOfAreaMembersForExport`. Admin only (`isAdminEmail` in the route, `requireAdminProfile` in the repository), `private, no-store`. Profiles hold a suburb NAME, not a postcode, so `placeForStoredSuburb` in `src/lib/geo.ts` walks the name back through the postcode table; a name that also exists inside Sydney counts as Sydney)

  **Overlapping events:** a host may run two of their own events at once (bug board #223/#273/#278). `database/069_allow_merchant_event_overlap.sql` drops the `prevent_merchant_event_overlap` trigger that refused it; `createEventForMerchant` returns `overlapsWith` so the create wizard names the clash in its success toast, and the admin queue flags a pending event that overlaps the same host's live one (`AdminEventRow.overlapsWith`) and asks for an "Approve anyway" confirm. Until 069 runs, the trigger still refuses the write and both paths translate its error.

- `api/admin/transactions/[id]/refund` (POST `{ amountCents?, reason? }` — manual Stripe refund; passes `settleBooking: true` because nothing else has released the seat or emailed the buyer), `api/admin/transactions/sync` (pulls recent charges/payouts back from Stripe), `api/admin/refund-failures/[id]` (POST `{ action: "retry" | "dismiss", note? }` — works one entry off the `refund_failures` queue; `retry` re-asks Stripe and does NOT pass `settleBooking`, because every writer of a failure row had already cancelled the seat, `dismiss` requires a note and sets `resolution = 'dismissed'`). All three guard with `isAdminEmail` directly, on top of `requireAdminProfile` inside the repository call.

  **Money queues:** `/admin/transactions` opens on a **Needs attention** tab whenever `refund_failures` has a pending row or `payment_disputes` has an open one, and the sidebar's Transactions badge counts the two together. Disputes are mirrored from `charge.dispute.*` webhooks into `payment_disputes` by `recordDisputeAudit` (`src/lib/stripe-sync.ts`), which still writes its audit_logs row - the table is current state, the log is history. Evidence is submitted in the Stripe Dashboard; the console only surfaces the deadline and deep-links out.

  **Trusted-merchant auto-approval:** `merchant_profiles.auto_approve_events` (migration `database/031_merchant_auto_approve_events.sql`) gates whether `createEventForMerchant` inserts an event as `pending` (untrusted → admin reviews, all admins get a "Event awaiting review" notification) or `live` (trusted → no review). Approving the MERCHANT turns the flag on (`updateMerchantVerificationForAdmin`; reject/suspend turns it off), and so does approving any one of their events; admins can revoke it from the merchant detail page. A trusted host's PAID event still lands `pending` until Connect has charges AND payouts on, and `updateMerchantConnectStatus` then publishes it by itself (`publishEventsHeldForPayouts` - audit row `publish_event_payouts_ready` + the `event-approved-merchant` email), so it never waits in the admin queue.
- `api/events`, `api/events/[eventId]`, `api/events/[eventId]/{bookmark,checkout,register}`, `api/events/[eventId]/waitlist/accept` (POST - a waitlisted attendee claims a promotion offer created by `cancelRegistration`; free events confirm in place + stamp `event_waitlists.accepted_at`, paid events return 402 → Stripe checkout). `api/events/[eventId]` GET also returns `bookingFeeCents` (per seat, from `booking_fee_bps`) so the Discover quick-view (`EventDetailModal`) can take a paid booking with +1s in place
- `api/guest-seats/[guestSpotId]/cancel` (POST - the purchaser hands back one +1 seat, refunded per policy, via `cancelGuestSeatForPurchaser`) and `api/guest-seats/[guestSpotId]/name` (POST `{ firstName, email?, dob? }` - the purchaser names or renames one +1 seat before the event via `nameGuestSeatForPurchaser`: same email = rename only; a new person = checkout's 18+/suppression/one-seat rules, a fresh claim token and the `guest-invite` email). Both drive `MyGuestSeats` on the event page
- `api/events/suggestions` (GET `?q=` — the typeahead behind the coordination drawer's "suggest something else" picker (runbook B1 `GET /events/suggestions?q=`). Signed-in only: `getProposalCatalogue` reads the caller's own bookings and bookmarks. **Search arm only** — an empty `q` answers `{ events: [] }` rather than the whole catalogue, because the three curated sections ("Events you're going to" / "Saved" / "You'd both like") are server-rendered with `/proposals` and the empty-query case must make no request at all. ≤20 rows, each fitting the PAIR (`cap.available >= 2`); the payload carries slug/title/suburb/start and no score, rank or section)

  **Google Sheets triage board** (`src/lib/support-sheets.ts`, service-account auth via `useJWTAccessWithScope=false` — Sheets rejects self-signed JWTs; no-ops until the `GOOGLE_*` env vars in `.env.example` are set): each new bug appends a row `URL (clickable HYPERLINK to the full origin) · Logged in as (reporter role) · What is wrong · What it should be · Is issue · AI fixed · Status · Screenshot · Date added · Ticket`. Rows are written by explicit next-empty-row update (not `append`, whose table-detection mis-fires on the checkbox columns), with grid auto-grow. Row colour is driven by **conditional formatting set up once on the sheet** (not imperative recolouring), so colours stay correct no matter who edits: Status `fixed` → 🟢 green, AI fixed ✓ → 🟠 amber, Is issue ✗ → ⚪ gray, else → 🔴 red. (`scripts/test-sheets.mjs` appends three demo rows to verify the connection.) Intended workflow: a Claude Code "AI fixer" pass reads open rows, fixes each, ticks **AI fixed** (amber); a human confirms by setting **Status = fixed** (green) or sends it back by un-ticking AI fixed (→ red). The widget's second tab is a per-page checklist of open bugs you tick off (PATCH → Status fixed → green).

  **AI-fixer pass — how to fix a bug from the [triage board](https://docs.google.com/spreadsheets/d/1q7nqA1Ngsf53zfX3_ReSjV18nFyIW8cN07M9c37W2W4/edit?gid=0#gid=0).** When asked to work the bug board, do this loop:

  1. **Read the open rows.** Run `node scripts/read-bugs.mjs` — it prints every row as JSON (`rowNum` + `cells`, including the HYPERLINK URLs for the page link and screenshot). The board columns are: `A` URL · `B` Logged in as · `C` What is wrong · `D` What it should be · `E` Is issue · `F` AI fixed · `G` Status · `H` Screenshot · `I` Date added · `J` Ticket (the `ticket_ref`) · `K` AI Comment. Work the 🔴 red rows — `Status` = `open` **and** `AI fixed` = FALSE. Skip rows already amber (`AI fixed` ✓), green (`Status` = `fixed`), or gray (`Is issue` ✗ — reporter/triager marked it not-a-bug).
  2. **Fix the code.** Use column `A` (the page URL → map to a file via the Page URI map above) plus `C`/`D` (what is wrong / what it should be) and the screenshot link to locate and fix the actual bug. Make a real change — don't tick the box without an edit.
  3. **Record the fix — sheet + Supabase in one step.** Run `node scripts/mark-ai-fixed.mjs <row> "Fixed X by doing Y"`. This ticks `AI fixed` (col `F` → 🟠 amber) and writes your change summary to `AI Comment` (col `K`) on the sheet, **and** sets `support_tickets.ai_fixed = true` + `ai_comment = '…'` in Postgres (matched by `ticket_ref`). Pass several bare row numbers (`node scripts/mark-ai-fixed.mjs 21 22 23`) to tick multiple rows at once with no comment. Always include a comment for a real fix so the human tester can read what changed in the Supabase Studio row drawer before confirming.
  4. **Do not set `Status` = `fixed` yourself.** That green flag is the human tester's confirmation. If they un-tick `AI fixed`, the row goes red again and you pick it up on the next pass.

The `ai_comment` column comes from migration `database/039_support_ticket_ai_comment.sql`.
