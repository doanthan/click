# Click — Event Detail (locked / unlocked / waitlist)

The full event page. Its **booking-state machine** is the whole job:
- **LOCKED** (not booked) — privacy state: suburb + distance only, venue **name & address HIDDEN**, FOMO/social proof (aggregate only), capacity bar, status tags, RSVP/pay CTA.
- **UNLOCKED** (booked / paid) — venue **revealed** (name, address, map, directions), "You're going", add-to-calendar, manage +1s, cancel (refund terms).
- **WAITLIST** (full) — "Join waitlist", waitlisted state; venue stays locked (no confirmed seat).

**🔴 Privacy rails (non-negotiable):**
- Venue **name hidden until booked** — LOCKED shows "Newtown · 1.4km · venue revealed when you RSVP". (claude design leaked "Posy Ceramics" on a locked page — never do that.)
- 🔴 **COORDINATION CONTEXT (Cindy 28 Jun):** when this page is reached from a click PROPOSAL (the coordination drawer's "RSVP" routes here — the user RSVPs the proposed event through the NORMAL flow on this page, not in the drawer), show a small calm banner at the TOP: **"RSVP to lock in your plan with [Name]"** (Lavender-tint, no ✨). Everything else is the normal Event Detail. On confirmed RSVP, return the user to the coordination state ("You're in — we'll let [Name] know"; both-booked → "you're both going"). Reached normally (not via a proposal), no banner. This is the ONE booking surface — never duplicate a checkout inside the drawer.
- **NO "click with" button on this page** — the event page is context-only. You click *with people*, after the event, never "into an event". Use **"Who's going"**, never "who's clicked in". The unlocked attendee cards (below) are **"view profile" only** — never a click affordance.
- **LOCKED is fully aggregate/anonymous:** ≥3 total attendees before any line shows; **never names/photos/per-person tags in LOCKED**; the romantic line is aggregate-only (≥3, dating-viewers only). Sensitive life tags never appear in LOCKED.
- **UNLOCKED (booked) named attendee cards — founder-approved, 27 Jun 2026 (⚠️ flag to Doan):** once you've booked, you may see who else is going as cards: **profile pic, name, shared INTEREST tags** (interests are public profile data — fine to show), and **"view profile"** (tap → profile drawer). **NO "click with" on these cards** (clicking is post-event only).
- **🔴 NO life tags on the attendee cards.** Life tags are SILENT by design — a person's individual life tags are never shown to anyone (`08` §0/§8 + RLS). The ONLY individual life-tag reveal is the post-mutual "we're the same" snapshot (non-sensitive shared tags, max 2, gated on an ACTIVE MUTUAL CLICK via `get_shared_life_tags`). Surfacing them on a pre-mutual attendee list breaks that gate and its RLS, and spends the post-mutual warmth early. Keep life tags off the named CARDS entirely — sensitive AND non-sensitive. (The **aggregate** who's-going FOMO line still uses them — "3 people over 50 are going", "a couple new to Sydney" — and the shared-viewer belonging signal, per `08` §4.3/§4.4. That's a count, never WHO.)
- **"Open to dating" per-card — only under MUTUAL OPT-IN:** shows on a card ONLY when BOTH the viewer and that attendee have dating mode visible ON; never to non-dating viewers, never for anyone who hasn't opted in. (This is already public-profile info for an opted-in user, so it's a modest softening of the event-page aggregate-only FOMO rule — ⚠️ flag to Doan to reconcile `10`/`12`.) Anyone can stay off attendee lists entirely via "Show me in event attendee lists". Scoped to UNLOCKED only — LOCKED stays fully aggregate/anonymous.

**🔴 Brand fixes from the live builds:** lowercase `click` + ✨ (NO tomato mascot); **drop "★ Founding venue"** (no founding programme); **countdown/cards are LIGHT on cream, never dark**; tags are **neutral, no `#hashtags`**; primary buttons **Deep Purple, never coral**; compact density (per GLOBAL).
